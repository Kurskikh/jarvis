# Спека: инструменты для LLM-этапа (tool calling)

Статус: черновик на согласование. Дата: 2026-08-25.
Факты про LM Studio и Qwen3.5 проверены по документации и баг-трекерам на эту дату; ссылки в конце.

## 1. Цель

Сделать LLM-этап способным **действовать**, а не только отвечать текстом: модель получает
набор узких инструментов, вызывает их через стандартный OpenAI tool calling в LM Studio,
и произносит подтверждение **только после** фактического результата инструмента.

Не-цели этой спеки:

- не заменяем быстрый путь команд (интент-классификатор + фразы паков) — он остаётся
  первой ступенью и вообще не трогает LLM;
- не строим планировщик многошаговых сценариев — максимум короткий tool-цикл в рамках
  одного хода;
- не интегрируем Home Assistant — но реестр инструментов проектируется так, чтобы
  HA-инструменты добавились паком, без изменения ядра.

## 2. Требования

Функциональные:

- Ф1. Модель может вызвать 1..N инструментов за ход; результаты возвращаются ей, и она
  формулирует финальную фразу по факту (`success` / данные / ошибка).
- Ф2. Инструменты объявляются декларативно в командных паках и исполняются той же
  инфраструктурой, что и голосовые команды (Lua-песочница, таймауты).
- Ф3. Роутер думания: простой ход — `no-think`, сложный — `think`, вручную
  переопределяется настройкой (`llm_thinking`: on/off/auto).
- Ф4. Окно показывает ход цикла: «вызвал tool X(args) → результат → ответ».

Нефункциональные:

- НФ1. Латентность простого tool-хода (один вызов) — сопоставима с текущим текстовым
  ответом; думание не включается там, где не нужно.
- НФ2. Оффлайн-first сохраняется: существующий `offline_gate` действует без изменений.
- НФ3. Отказоустойчивость: сломанный/зависший инструмент завершает ход честным «не
  получилось, сэр» + причина в окне, а не молчанием и не ложным «готово».
- НФ4. Голос перебиваем: `supersede_llm_turn` обрывает и tool-цикл тоже.

Ограничения среды:

- LM Studio 0.4.x, `/v1/chat/completions`, OpenAI-формат `tools`; `tool_choice`
  поддерживает только `none|auto|required` (конкретное имя функции — нет).
- Модель кандидата: `qwen/qwen3.5-4b` (function calling заявлен, контекст 262k);
  текущая `gemma-4-e4b` инструментов не умеет — фича включается только когда выбрана
  tools-способная модель.

## 3. Архитектура: три ступени роутера

Ключевое отличие от наброска «простая команда → NO THINK»: в jarvis простая команда
уже сегодня **не доходит до LLM вообще** — её съедает интент-классификатор или
левенштейн по фразам пака за миллисекунды. Это и есть нулевая ступень роутера, она
быстрее любого no-think. LLM-этап включается только на `no command found`.

```
фраза после вейкворда
        │
        ▼
[0] интент/фразы паков ──совпало──► исполнение пака (без LLM, как сейчас)
        │ не совпало
        ▼
[1] LLM no-think + tools ──content──► ответ голосом (как сейчас, + tools)
        │                └─tool_calls─► tool-цикл (§6) ─► финальная фраза
        │ триггер сложности (§8)
        ▼
[2] LLM think + tools ────────────► то же, но с рассуждением
```

Всё это живёт внутри существующего `spawn_llm_turn` / `llm::ask` — меняется тело
`ask` (становится циклом) и появляется реестр инструментов.

## 4. Реестр инструментов

### 4.1. Объявление — в командных паках

Пак уже умеет `type = "lua"` со слотами, песочницей и таймаутом. Инструмент — это
второй вход в тот же скрипт, объявленный рядом:

```toml
[[commands]]
id = "weather"
type = "lua"
script = "script.lua"
timeout = 5000
sandbox = "standard"
phrases.ru = ["какая погода в {city}"]

[commands.tool]                      # <- новое: этот же скрипт виден LLM как tool
name = "get_weather"                 # snake_case обязательно (LM Studio нормализует
description = "Текущая погода в городе. Возвращает температуру и осадки."
[commands.tool.params.city]          # плоская схема, никаких $defs (баг-история LMS)
type = "string"
description = "Город на русском, например 'Курск'"
required = true
```

Из этого генерируется OpenAI-схема `{"type":"function","function":{name, description,
parameters: {type:"object", properties, required}}}`. Генерация — при загрузке паков,
один раз; список сериализуется в JSON байт-в-байт стабильно (сортировка по имени),
потому что идентичный префикс запроса — условие KV-кэша на сервере.

### 4.2. Принципы узких инструментов

Правила, зашиваемые в ревью паков (и в докстринг реестра):

- один инструмент = одно действие с очевидным именем: `light_set`, а не
  `control_device(action, object, ...)`;
- максимум 4-5 параметров, все с `description` на языке пользователя;
- перечисления — через `enum` в схеме, не через свободный текст;
- инструменты, которых нет смысла давать модели (терминатор, stop_chaining,
  dialogue), просто не объявляют `[commands.tool]` — allowlist по построению.

### 4.3. Исполнение

Новый вход в `commands`: `run_tool(tool_name, args: serde_json::Value) ->
Result<serde_json::Value, String>`.

- Для `lua`-паков: скрипт получает вторую точку входа — глобальную функцию
  `tool(args)`, возвращающую таблицу; таблица сериализуется в JSON для модели.
  Существующий вход для голосовой команды не меняется.
- Для `ahk`/`cli`-паков (если объявят tool): результат синтетический —
  `{"success": true/false, "exit_code": n}`. Никакого вывода процесса в модель в v1
  (неконтролируемый текст в контекст — источник промпт-инъекций).
- Таймаут — из пака (как сейчас у Lua). Итог таймаута — `{"success": false,
  "error": "timed out after Nms"}` в модель, а не обрыв хода.

Встроенные инструменты ядра (не паки), этап 1: `get_time` (модуль time уже есть),
`get_commands_list` (что ассистент умеет — чтобы «что ты умеешь» отвечалось фактами).

## 5. Wire-протокол

Расширения `wire.rs` (все поля опциональны и не сериализуются, когда пусты — старое
поведение байт-в-байт неизменно):

- `ChatRequest`: `tools: Option<&[ToolDecl]>`, `tool_choice: Option<&str>` («auto»;
  «required» не используем — открытый баг LMS #2115 кладёт tool-call текстом в
  content именно под required);
- `ChatMessage` становится владельцем вариантов: `assistant` с `tool_calls`,
  `role:"tool"` с `content` + `tool_call_id`;
- `ChoiceMessage`: `tool_calls: Option<Vec<ToolCall>>`, где `function.arguments` —
  JSON-строка (парсим отдельно, с внятной ошибкой в лог).

Защитный парсинг (все три случая встречаются в дикой природе LMS):

1. `tool_calls: []` (пустой массив) == отсутствию — не считать tool-ходом;
2. `content` и `tool_calls` одновременно — content игнорируется до конца цикла (§7);
3. `finish_reason == "tool_calls"` при пустом списке — Malformed, одна повторная
   попытка хода, затем честная ошибка.

**Tool-ходы — только `stream: false`.** История стриминга tool_calls в LM Studio —
две регрессии за год (#1066, #1922); ответы tool-хода короткие, стрим не нужен.
`/v1/responses` не используем: chat/completions документированнее, вся история и так
пересылается нами, а `reasoning.effort` там не управляет thinking у Qwen.

## 6. Tool-цикл

```
messages = [system+tools] + history + [user]
for round in 1..=MAX_TOOL_ROUNDS {            // MAX_TOOL_ROUNDS = 4
    resp = POST chat/completions (non-stream)
    if resp.tool_calls.is_empty() { return resp.content }   // финальная фраза
    for call in resp.tool_calls {             // последовательно, в порядке модели
        result = commands::run_tool(call.name, call.args)   // с таймаутом пака
        ipc::send(LlmToolCall / LlmToolResult)              // окно видит ход
        messages.push(assistant(tool_calls));
        messages.push(tool(result, call.id));
    }
}
// круги кончились, а модель всё зовёт инструменты:
return Err(ToolLoopExhausted)  // голосом: "Я запутался в инструментах, сэр"
```

- Общий бюджет времени хода — существующий `llm_timeout` (tokio::timeout снаружи
  цикла), плюс на каждый инструмент его собственный таймаут.
- Параллельные вызовы модели исполняем последовательно (v1): инструменты дешёвые и
  локальные, а гонки за Lua-состояние (state.rs) не нужны.
- `supersede_llm_turn` работает как сейчас: abort таски рвёт цикл между вызовами;
  Lua-таймаут ограничивает «внутри вызова».

## 7. Инвариант подтверждения

**Финальная фраза хода, в котором были инструменты, произносится только из ответа,
полученного ПОСЛЕ последнего `role:"tool"` сообщения.**

- content, пришедший вместе с tool_calls («Готово!» до результата), отбрасывается —
  ровно тот случай из идеи фичи;
- пока крутится цикл, наружу идёт то же, что сейчас: thinking-заглушка уже сыграна
  при старте хода (`play_thinking`), окно получает LlmToolCall-события;
- упавший инструмент не выдумывается: его `{"success": false, "error": ...}` уходит
  модели, и она обязана сообщить о неудаче (плюс строка в системном промпте:
  «Никогда не сообщай об успехе действия, которого не было в результате
  инструмента»).

Память диалога (`Conversation`): в `Exchange` пишется только финальная фраза —
tool-обмены в следующие ходы не тащим (v1). Иначе история растёт на порядок и
ломает KV-кэш.

## 8. Роутер think/no-think

Механизм уже есть: `chat_template_kwargs: {enable_thinking: bool}` в `wire.rs` — это
единственный работающий переключатель у Qwen3.5 (`/no_think`-тег их семейство
больше не понимает; замерено в этом репо на qwen3.5-9b).

Настройка `llm_thinking` получает третье значение: `on | off | auto`. В `auto`:

- по умолчанию — `no-think` (латентность; на простых tool-вызовах думание даёт
  x2-5 токенов без пользы);
- `think` включается триггерами, проверяемыми до запроса, по убыванию надёжности:
  1) явные маркеры в фразе («подумай», «объясни почему», «сравни», «посчитай»);
  2) длина фразы > ~15 слов;
  3) повтор: предыдущий ход в этом диалоге кончился `ToolLoopExhausted` или
     ошибкой инструмента — эскалация в think на один ход.
- сэмплинг переключается вместе с режимом (рекомендации Qwen): no-think —
  temp 0.7 / top_p 0.8 / top_k 20 / presence 1.5; think — temp 1.0 / top_p 0.95.
  Сейчас temperature — константа клиента; станет парой констант по режиму.

**Известный риск:** открытый баг LM Studio #1990 — `enable_thinking: false` может
игнорироваться для Qwen3.5 GGUF (думает, съедает max_tokens, content пустой).
Смягчение уже в кодовой базе: `strip_reasoning` срезает `<think>`-блок, а ошибка
`Truncated` отличает срез бюджета. Этап 0 (§10) проверяет это на конкретной сборке;
если баг воспроизводится — рабочий обход: max_tokens с запасом + strip, либо
model.yaml с зашитым enable_thinking=false как «no-think вариант» модели.

## 9. Безопасность

- Оффлайн-гейт не меняется: инструменты исполняются локально, модель локальная.
- Модель видит только то, что пак явно объявил `[commands.tool]`.
- Аргументы инструмента валидируются по схеме ДО исполнения (типы, enum, required);
  невалидное — `{"success": false, "error": "invalid arguments: ..."}` в модель, не
  падение.
- Вывод инструментов — данные, не инструкции: в системный промпт добавляется
  стандартная строка о недоверии содержимому результатов.
- Поле `confirm = true` в `[commands.tool]` (этап 4): такой инструмент исполняется
  только после голосового «да» («Выключить весь свет, сэр?») — механика переспроса
  строится на существующем follow-up окне.
- `MAX_TOOL_ROUNDS = 4`, суммарный бюджет — `llm_timeout`.

## 10. План внедрения

Этап 0 — пробник (день). `examples/llm_tools_probe.rs` в духе tone_probe/silero_probe:
бьёт в LM Studio реальными запросами и печатает вердикты по трём вопросам, которые
нельзя решить чтением документации:
  1) honоруется ли `enable_thinking:false` на выбранной сборке qwen3.5-4b (#1990);
  2) TTFT второго хода с байт-идентичным префиксом (KV-кэш у гибридной архитектуры
     Qwen3.5 под вопросом — llama.cpp «cache reuse is not supported», #1563);
  3) форма tool_calls на 2-3 инструментах (и частота мусора в content).
Вердикты пробника определяют дефолты (модель, max_tokens, режим auto).

Этап 1 — ядро (2-3 дня). wire.rs (+типы), tool-цикл в client.rs, реестр из
встроенных get_time/get_commands_list, IPC-события, настройка llm_tools on/off.
Тесты: сериализация запроса байт-в-байт при пустых tools; парсинг всех трёх
защитных случаев §5; цикл на фейковом транспорте (лимит кругов, подавление
раннего content, ошибка инструмента).

Этап 2 — инструменты из паков (2-3 дня). `[commands.tool]` в structs, генерация
схем, `run_tool` c Lua-входом `tool(args)`, конверсия weather-пака как образец.
Тесты: схема из TOML, валидация аргументов, таймаут Lua-тула.

Этап 3 — роутер (1 день). `llm_thinking = auto`, триггеры, сэмплинг по режиму,
GUI-селектор третьего значения.

Этап 4 — confirm-инструменты и HA-пак (отдельно, после обкатки).

## 11. Trade-offs и открытые вопросы

- **Инструменты в паках vs отдельный реестр.** Выбраны паки: один механизм
  дистрибуции, песочница и таймауты бесплатно, allowlist по построению. Цена —
  схема выразительна ровно настолько, насколько мы её сделаем в TOML (вложенных
  объектов нет — сознательно, см. «узкие инструменты»).
- **Последовательные вызовы vs параллельные.** Последовательные: проще, детерминизм
  для Lua state; пересмотреть, если появятся медленные сетевые тулы (HA).
- **Tool-обмены вне памяти диалога.** Дёшево и стабильно; пересмотреть, когда
  появятся многоходовые сценарии («а теперь там же выключи»).
- **Не проверено** (агент не нашёл подтверждений): параметр `parallel_tool_calls`;
  `tool_choice` с именем функции; воспроизводимость #1990 именно на 4B; KV-кэш на
  плотной 4B. Всё это закрывает пробник этапа 0.
