# Спека: инструменты для LLM-этапа (tool calling)

Статус: черновик, ревизия 2 после ревью реализуемости. Дата: 2026-08-25.
Факты про LM Studio, Qwen3.5 и про текущий код Джарвиса проверены по документации,
баг-трекерам и исходникам на эту дату; ссылки и номера строк по месту.

Ревизия 2 переписывает разделы после ревью, которое поймало шесть блокеров в
ревизии 1: tool-цикл в диалоге, неверный порядок сообщений протокола, необеспеченный
инвариант подтверждения, мнимую отменяемость Lua, несовместимый контракт «тот же
скрипт» и недооценённый объём. Все замечания подтверждены по коду и приняты.

## 1. Цель

Сделать LLM-этап способным **действовать**, а не только отвечать текстом: модель
получает набор узких инструментов, вызывает их через стандартный OpenAI tool calling
в LM Studio, и произносит подтверждение **только после** фактического результата.

Не-цели:

- не заменяем быстрый путь команд (интент-классификатор + фразы паков) — он остаётся
  первой ступенью и вообще не трогает LLM;
- не строим многошаговый планировщик — максимум короткий tool-цикл в одном ходе;
- не интегрируем Home Assistant, но реестр проектируется так, чтобы HA добавился паком.

## 2. Что нужно исправить относительно наивного подхода (принятые замечания ревью)

Прежде чем описывать реализацию — шесть мест, где «просто встроить tool-loop в
`llm::ask`» ломается о текущий код. Каждое проверено по исходникам.

### 2.1. Инструменты не должны появляться в режиме диалога

Диалог намеренно не исполняет команды: разговорная фраза не должна ничего запускать —
это прямо задокументировано в [app.rs](../../crates/jarvis-app/src/app.rs) (комментарий
к `enum Mode`, «Matching commands inside a dialogue was considered and left out on
purpose»). Если tool-цикл окажется внутри `llm::ask`, инструменты потекут и в диалог, и
в fallback без разбора. Решение — **политика инструментов на каждый ход** (§4).

### 2.2. Порядок сообщений в цикле был неверный

В ревизии 1 псевдокод добавлял `assistant(tool_calls)` внутри цикла по вызовам — при
двух инструментах вышло бы два assistant-сообщения. Правильно (и так требует
[документация LM Studio](https://lmstudio.ai/docs/developer/openai-compat/tools)): **одно**
assistant-сообщение со всеми `tool_calls`, затем подряд по одному `role:"tool"` на
каждый вызов. Исправлено в §6.

Плюс: на последнем круге инструменты исполнялись, но их результаты модель уже не
видела — цикл сразу отдавал `ToolLoopExhausted`. Исправлено: предельный круг делает
финальный запрос с `tool_choice:"none"` (§6).

### 2.3. Инвариант «не соврать об успехе» не был обеспечен

LM Studio прямо документирует: если парсер не распознал tool-синтаксис модели, сырой
`<tool_call>` попадёт в обычный `content` (баг #2115 — под `tool_choice:"required"`
именно так). Наивный алгоритм счёл бы это финальным ответом и произнёс XML или ложное
«готово». Один системный промпт это не закрывает. Решение — хостовый `ToolOutcome` и
фильтр tool-markup (§7).

### 2.4. Таймаут и отмена Lua работают не так, как казалось

Таймаут Lua — это инструкционный хук раз в 1000 инструкций
([engine.rs](../../crates/jarvis-core/src/lua/engine.rs)). Он **не прерывает** блокирующий
HTTP с собственным 30-секундным таймаутом
([http.rs](../../crates/jarvis-core/src/lua/api/http.rs)), `sleep` или `Command::output()` —
во время такого вызова Lua не исполняет инструкций, и хук не срабатывает. Значит
`tokio::timeout` снаружи и `JoinHandle::abort()` не оборвут синхронный `run_tool` до
его возврата. Честная модель отмены — в §8.

### 2.5. «Тот же скрипт, новая `tool(args)`» несовместимо с паками

Lua-файл исполняется целиком при загрузке
([engine.rs](../../crates/jarvis-core/src/lua/engine.rs) — `load(...).eval()`), а weather
делает HTTP, уведомление и звук прямо на верхнем уровне
([script.lua](../../resources/commands/weather/script.lua)). Чтобы найти глобальную
`tool`, файл пришлось бы выполнить — побочные эффекты уже произойдут. Решение —
**отдельный `tool.lua`, который только объявляет функцию** (§5.3).

### 2.6. AHK и CLI не годятся в первый релиз

`execute_exe`/`execute_cli` возвращают `Child` сразу после `spawn()`, без `wait()`
([commands.rs](../../crates/jarvis-core/src/commands.rs)) — фактический результат
процесса неизвестен, честный `exit_code` вернуть нельзя. AHK/CLI-инструменты
**исключены из v1** целиком; для них нужен отдельный process runner с ожиданием,
таймаутом, kill-tree и без подстановки модельных строк в `cmd /C`.

## 3. Архитектура: три ступени роутера + слой оркестрации

Быстрый путь команд — нулевая ступень: простая команда съедается интентом/фразами за
миллисекунды, вообще без LLM. LLM включается только на «команда не найдена».

```
фраза после вейкворда
        │
        ▼
[0] интент/фразы паков ──совпало──► исполнение пака (без LLM)
        │ не совпало / режим диалога
        ▼
[1] LLM no-think + tools(policy) ──content──► ответ голосом
        │                        └─tool_calls─► tool-цикл (§6) ─► финальная фраза
        │ триггер сложности (§9)
        ▼
[2] LLM think + tools ────────────► то же, с рассуждением
```

**Оркестрация живёт НЕ в `llm::ask`.** `llm::ask` остаётся тонким транспортом одного
запроса (его дёргает и jarvis-cli, где Lua нет вовсе). Tool-цикл — новый слой
`llm::turn` (или `jarvis-app::llm_turn`), который склеивает транспорт `llm::ask`,
реестр инструментов и IPC. Так CLI по-прежнему получает LLM без Lua, а связывание
Lua+IPC не протекает в ядро транспорта.

## 4. Политика инструментов на ход

Каждый ход получает `ToolPolicy`, вычисляемую из режима и настроек ДО запроса:

- `Disabled` — режим диалога: модель знает про голосовые команды, но инструментов не
  получает; в системный промпт кладётся строка «чтобы выполнить действие, назови
  активационную фразу и команду». Никакие `tools` в запрос не уходят.
- `ReadOnly` — fallback вне диалога, действий не разрешено: только читающие
  инструменты (`get_time`, `get_commands_list`, `get_weather`).
- `Actions` — fallback, действия разрешены (после обкатки и §10): read-only +
  изменяющие состояние инструменты, помеченные `confirm`.
- прямые команды — как сейчас, без LLM.

`get_commands_list` различает `voice_only` и `tool_callable`, а не отдаёт общий
список: в `Disabled` он перечисляет голосовые команды и объясняет, как их вызвать; в
`ReadOnly`/`Actions` — что доступно как инструмент.

**Удалённая модель ⇒ tools принудительно off** (v1): при `llm_allow_remote` политика
падает до `Disabled` независимо от настроек. Отдельный флаг `llm_allow_remote_tools`
для тонкой настройки — позже; в v1 достаточно жёсткого запрета, чтобы удалённая модель
не управляла локальными инструментами.

## 5. Реестр инструментов

### 5.1. Объявление в паке

```toml
[[commands]]
id = "weather"
type = "lua"
script = "script.lua"          # голосовой вход, как сейчас — НЕ трогается
timeout = 5000
sandbox = "standard"
phrases.ru = ["какая погода в {city}"]

[commands.tool]
name = "get_weather"           # snake_case (LM Studio нормализует имена)
description = "Текущая погода в городе. Возвращает температуру и осадки."
kind = "read_only"             # read_only | action; action требует §10
script = "tool.lua"            # ОТДЕЛЬНЫЙ файл, только объявляет функцию (§5.3)
timeout = 8000                 # свой бюджет; см. §8 про его реальные пределы
[commands.tool.params.city]
type = "string"                # плоская схема, без $defs (баг-история LMS)
description = "Город на русском, например 'Курск'"
required = true
```

Из этого генерируется OpenAI-схема `{"type":"function","function":{name, description,
parameters}}` — один раз при загрузке паков, сериализация байт-в-байт стабильна
(сортировка по имени): идентичный префикс запроса — условие KV-кэша сервера.

### 5.2. Принципы узких инструментов

- один инструмент — одно действие с очевидным именем: `light_set`, не
  `control_device(action, object, ...)`;
- до 4–5 параметров, все с `description` на языке пользователя, перечисления через
  `enum`;
- инструменты, которых не должно быть у модели (терминатор, stop_chaining, dialogue),
  просто не объявляют `[commands.tool]` — allowlist по построению;
- **локализованные описания.** Сейчас во всех 39 командах поле `description`
  отсутствует вовсе (проверено), а модель без описаний зовёт инструменты наугад.
  Описания нужны на языке интерфейса — это отдельная работа наполнения, не побочный
  эффект.

### 5.3. Исполнение

Новый вход `commands::run_tool(name, args) -> Result<Value, String>`.

- Только `type = "lua"` паки с `kind = "read_only"` в v1. Скрипт — отдельный
  `tool.lua`, который **только объявляет** глобальную `function tool(args)`,
  возвращающую таблицу, и ничего не делает на верхнем уровне (§2.5). Движок исполняет
  файл (объявление функции — без эффектов), затем вызывает `tool(args)`.
- Валидация аргументов по схеме ДО вызова (типы, enum, required): невалидное —
  `{"success": false, "error": "invalid arguments: ..."}` в модель, не вызов.
- Лимиты размера: аргументы и результат обрезаются/отклоняются по потолку (напр. 8 КБ
  результата), чтобы инструмент не залил контекст.
- AHK/CLI — не в v1 (§2.6). Встроенные тулы ядра v1: `get_time`, `get_commands_list`.

## 6. Wire-протокол и tool-цикл

Расширения `wire.rs` опциональны и не сериализуются пустыми — старое поведение
байт-в-байт. `tool_choice` — `"auto"` в рабочих кругах (под `"required"` баг #2115
кладёт вызов текстом в content), `"none"` на финальном круге. **Tool-ходы — только
`stream:false`** (две регрессии стриминга tool_calls за год: #1066, #1922).
`/v1/responses` не используем.

Защитный парсинг четырёх реальных случаев: пустой `tool_calls: []` == отсутствие;
content вместе с tool_calls — content игнорируется до конца цикла; `finish_reason:
"tool_calls"` без списка — одна повторная попытка, затем ошибка; **content, похожий на
tool-markup** (`<tool_call>`, `<function=`, `[TOOL_REQUEST]`) — никогда не финальный
ответ (§7).

```
messages = [system(+tools по policy)] + history + [user]
calls_made = 0
for round in 1..=MAX_TOOL_ROUNDS {          // MAX_TOOL_ROUNDS = 4
    choice = if round == MAX_TOOL_ROUNDS { "none" } else { "auto" }
    resp = POST chat/completions (non-stream, tool_choice = choice)
    if resp.tool_calls.is_empty() {
        return final_reply(resp.content)    // прошёл фильтр markup (§7)
    }
    // ОДНО assistant-сообщение со всеми вызовами, затем результаты подряд
    messages.push(assistant(resp.tool_calls))
    for call in resp.tool_calls {
        calls_made += 1
        if calls_made > MAX_TOOL_CALLS { return err(TooManyCalls) }   // = 8
        if seen(call) { result = dedup_error() }        // защита от повтора
        else { result = commands::run_tool(call.name, call.args) }    // §8
        ipc::send(LlmToolCall{request_id, tool_call_id, round, name, args})
        ipc::send(LlmToolResult{request_id, tool_call_id, status})
        messages.push(tool(result, call.id))
    }
}
// финальный круг был tool_choice:"none" — модель обязана была ответить текстом;
// если и тут пусто — хостовая детерминированная фраза (§7)
```

Два независимых лимита: `MAX_TOOL_ROUNDS = 4` (круги) и `MAX_TOOL_CALLS = 8` (всего
вызовов за ход). Параллельные вызовы модели исполняются последовательно (v1): тулы
локальные, а Lua-state (state.rs) не любит гонок.

## 7. Инвариант подтверждения (хостовый, не промптом)

Приложение ведёт `ToolOutcome` по каждому вызову и решает финал САМО, не доверяя
формулировке модели:

- **Финальная фраза произносится только из ответа, полученного после последнего
  `role:"tool"`** и только если она прошла фильтр tool-markup.
- content, похожий на сырой tool-вызов, никогда не озвучивается — это нераспознанный
  парсером вызов (#2115), а не ответ.
- **Действие подтверждается вслух только при фактическом `success == true`** из
  `ToolOutcome`. Инструмент упал — детерминированная фраза хоста об ошибке (с
  причиной в окне), не импровизация модели.
- Действие выполнилось, но финальный запрос к LLM упал — хост сам говорит «Действие
  выполнено, но сформулировать ответ не удалось», а не молчит и не выдумывает.
- Строка в системном промпте («не сообщай об успехе действия, которого нет в
  результате инструмента») остаётся, но как второй рубеж, не как гарантия.

Память диалога (`Exchange`): только финальная фраза; tool-обмены в следующие ходы не
тащим (v1) — иначе история растёт на порядок и ломает KV-кэш.

## 8. Отмена и таймаут инструмента — честная модель

Инструкционный хук Lua не прерывает блокирующий I/O (§2.4). Поэтому v1:

- `run_tool` исполняется на `spawn_blocking`; снаружи гонка с `tokio::timeout` по
  бюджету инструмента. По таймауту в модель уходит `{"success": false, "error":
  "timed out"}`, а голосовой ход продолжается.
- **Честно фиксируется:** уже начатый I/O-вызов внутри Lua неотменяем — он доработает
  в фоне (тред занят до возврата). Отмена (`supersede_llm_turn`) и таймаут
  гарантируют лишь, что **последующие** вызовы не пойдут и результат не будет озвучен,
  а не мгновенную остановку текущего.
- Смягчение сейчас: снизить встроенный таймаут `jarvis.http` с 30с до бюджета
  инструмента, чтобы разрыв не превышал ожидание.
- Настоящее решение (позже, обязательно до `action`-тулов с внешними эффектами):
  либо cooperative deadline во все Lua API (http/sleep/process проверяют дедлайн),
  либо исполнение опасных инструментов в отдельном убиваемом процессе.

## 9. Роутер think / no-think

Переключатель уже есть: `chat_template_kwargs: {enable_thinking: bool}` в `wire.rs` —
единственный работающий у Qwen3.5 (тег `/no_think` семейство больше не понимает;
замерено в этом репо на 9B). `llm_thinking = on | off | auto`; в `auto` по умолчанию
no-think, think — по триггерам до запроса: маркеры («подумай», «объясни», «сравни»),
длина > ~15 слов, эскалация на один ход после `ToolLoopExhausted`/ошибки инструмента.
Сэмплинг по режиму (карточка Qwen3.5-4B): no-think — temp 0.7 / top_p 0.8 / top_k 20 /
presence 1.5; think — temp 1.0 / top_p 0.95.

**`think + tools` по умолчанию ВЫКЛЮЧЕН**, включается только после успешного пробника
конкретной сборки: открытый баг #1990 — `enable_thinking:false` может игнорироваться
на Qwen3.5 GGUF (думает, съедает max_tokens, content пустой), и `strip_reasoning` не
спасёт, если reasoning съел весь бюджет. Обход при воспроизведении — max_tokens с
запасом либо model.yaml-вариант с зашитым no-think.

## 10. Безопасность — предпосылки для action-тулов

Read-only MVP этого не требует, но **до любых изменяющих состояние инструментов**
нужно закрыть (проверено по коду):

- **IPC без аутентификации.** `handle_client`
  ([server.rs](../../crates/jarvis-core/src/ipc/server.rs)) принимает любого клиента без
  токена и без проверки Origin — локальная программа или открытая веб-страница может
  слать `TextCommand` и читать broadcast. Нужны IPC-токен и Origin-policy. *(Это
  предсуществующая уязвимость, не вносится этой фичей — вынесена в отдельную задачу; но
  action-тулы без неё включать нельзя.)*
- **Выход из песочницы через `..`.** `resolve_path`
  ([fs.rs](../../crates/jarvis-core/src/lua/api/fs.rs)) при несуществующем пути падает в
  неканонизированный `resolved`, и `starts_with` проходит лексически — `..` уводит за
  пределы пака. Чинить containment. *(Тоже предсуществующая — отдельная задача.)*
- **Удалённая модель не управляет тулами** — §4 (в v1 жёсткий off, позже отдельный
  флаг).
- **`confirm` — обязательное условие любого мутирующего действия**, не «этап
  когда-нибудь». И follow-up НЕ является подтверждением: это просто продлённое обычное
  слушание, следующая «да» уходит в обычный роутинг, не привязанная к отложенному
  действию. Нужна отдельная pending-confirmation state machine: действие ставится в
  ожидание, озвучивается вопрос, и только связанное «да»/«нет» его исполняет или
  отменяет.
- Вывод инструментов — данные, не инструкции (строка о недоверии в системном промпте).

## 11. Объём интеграции (не недооценивать)

- **Редактор паков молча выкинет `[commands.tool]`.** Сериализатор
  ([commands_editor.rs](../../crates/jarvis-gui/src/commands_editor.rs)) рукописный и
  эмитит только известные поля — обычное сохранение удалит новую секцию. Расширять
  сериализатор вместе со схемой.
- **Неизменяемый snapshot реестра на весь ход.** `commands_list()` уже отдаёт
  `Arc`-снимок; tool-реестр тоже снимается один раз в начале хода, чтобы reload между
  объявлением и исполнением не подменил инструмент.
- **Слой оркестрации вне `llm::ask`** (§3): CLI включает LLM, но не Lua.
- **IPC-события** несут `request_id`, `tool_call_id`, `round`, `status` — окно видит
  ход по шагам.
- **Детерминированный ответ на «что ты умеешь»**: не полагаться на то, что модель сама
  вызовет `get_commands_list` — дать прямой хостовый путь.

## 12. План внедрения и MVP

**MVP, который стоит согласовывать:**

- только built-ins + один read-only Lua-тул через отдельный `tool.lua`;
- tools выключены в диалоге и для удалённой модели;
- ни AHK, ни CLI, ни мутирующих действий;
- исправленный цикл сообщений, хостовое подтверждение (`ToolOutcome`), лимиты, фильтр
  tool-markup;
- `think + tools` по умолчанию off.

**Этап 0 — пробник (день).** `examples/llm_tools_probe.rs` в духе tone/silero-пробников.
Бьёт в LM Studio и печатает вердикты по вопросам, не решаемым чтением документации:
  1) хонорируется ли `enable_thinking:false` на выбранной сборке (#1990);
  2) TTFT второго хода с байт-идентичным префиксом — KV-кэш гибридной Qwen3.5 под
     вопросом (#1563);
  3) корректность выбора инструмента, форма аргументов, частота ложных вызовов и мусора
     в content — **на репрезентативном наборе примерно из 10 объявлений** (не 2–3 и не
     на несуществующих финальных паках), P50/P95, холодная/тёплая модель, совместная
     VRAM-нагрузка с TTS-сайдкаром.
Вердикты определяют дефолты (модель, max_tokens, режим, включать ли think+tools).

**Этап 1 — ядро (3–4 дня).** Слой оркестрации `llm::turn`, wire.rs (+типы),
исправленный цикл (§6), `ToolOutcome` и фильтр markup (§7), политика хода (§4),
built-ins, IPC-события с полями (§11), настройка `llm_tools`. Тесты: байт-в-байт при
пустых tools; четыре защитных случая парсинга; порядок сообщений (одно assistant + N
tool); лимиты кругов и вызовов; подавление раннего/markup content; финальный круг с
`tool_choice:none`; отказ инструмента → детерминированная фраза.

**Этап 2 — read-only тул из пака (2–3 дня).** `[commands.tool]` + `kind`+`tool.lua` в
structs, генерация схем, `run_tool` на spawn_blocking с таймаутом (§8), сериализатор
редактора, weather как образец. Тесты: схема из TOML, валидация аргументов, таймаут,
неизменяемый snapshot.

**Этап 3 — роутер (день).** `llm_thinking = auto`, триггеры, сэмплинг по режиму,
GUI-селектор.

**Этап 4 — action-тулы.** Только после §10: IPC-auth, fs-containment,
pending-confirmation state machine, `confirm`-обязательность, идемпотентность
мутирующих действий (эта проблема относится сюда, а не к read-only MVP — в MVP
мутаций нет), отдельный process runner для AHK/CLI, `llm_allow_remote_tools`.

## 13. Trade-offs и открытые вопросы

- **Тулы в паках, не отдельный реестр:** один механизм дистрибуции, песочница и
  allowlist бесплатно; цена — плоская схема без вложенных объектов (сознательно).
- **Последовательное исполнение:** проще и детерминированно; пересмотреть при
  медленных сетевых тулах.
- **Tool-обмены вне памяти диалога:** дёшево; пересмотреть для сценариев «а теперь там
  же…».
- **Не проверено** (закрывает пробник): `parallel_tool_calls`; `tool_choice` по имени;
  #1990 именно на 4B; KV-кэш на плотной 4B; умеет ли инструменты конкретный
  `gemma-4-e4b-heretic`-квант — официальная страница Gemma заявляет tool calling, но
  решает пробник точного файла/шаблона/рантайма, а не общая формулировка.
